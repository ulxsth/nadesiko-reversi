# 元実装との差分

参照元: <https://github.com/2509-hackz-ichthyo/main>

## 維持する体験

- 8×8盤面と中央4駒の初期配置
- 0〜255のグレースケール駒
- 挟んだ駒を`(a1+a2+b1)/3`で中間色へ変える（丸め方はルール版2で変えた）
- 最終盤面の平均色で黒寄り・白寄りを決める（同点の扱いはルール版2で変えた）
- 二人対戦と対局再生へ拡張できる状態モデル

## 意図的に変える点

### 固定端色を最遠駒に統一

元実装のコメントは最遠の挟み駒を`a2`と説明するが、コードの一部は変換対象末尾を参照する。v1契約ではコメントどおり最遠の固定端を使い、全色を着手前盤面から同時計算する。

### 乱数をseed付きLCGへ変更

元実装は実行時刻seedのGo乱数を使う。v1は再現可能な棋譜と複数runtime間の一致を優先し、32bit LCGを契約化する。

### 行き詰まり終了を追加

元実装は盤面が満杯の場合だけ終了し、合法手がない場合の終了はTODOになっている。v1は合法手がない場合のパスと、二者連続パスでの終了を定義する。

### 色変換の丸めと同点の扱いを変え、盤面互換性を捨てる（ルール版2）

元実装は色変換を`floor((a1+a2+b1)/3)`で常に切り捨て、平均が127.5ちょうどの終局を二分岐の`else`側として`light`の勝ちにしていた。ルール版1はこれをそのまま写した。

切り捨ては1変換あたり平均1/3の色を0（黒）側へ漏らすため、局面が進むほど`dark`が有利になる。60手の実対局では延べ354駒が変換され、期待損失は約118色単位で、判定閾値8160に対して接戦でだけ効く。127.5ちょうどの`light`勝ちも設計判断ではなく、色の重心という単一の評価軸の外から持ち込まれた扱いだった。

ルール版2では丸めを四捨五入（`floor((2S+3)/6)`）へ変え、`2*色合計 == 駒数*255`を引き分け（`winner`=`null`）とする。

**この変更で元実装との盤面互換性は完全に失われる。** 同じseedと同じ着手列からでも別の盤面になり、勝敗も変わりうる。公平性を優先した意図的な非互換で、版`1`の棋譜は`record_unsupported_rules_version`で明示的に拒否する。

### サーバーを盤面の正本にする

元実装にはクライアント側とLambda側へゲーム判断が分散している箇所がある。v1はルールruntimeの結果だけを確定状態とし、UIは成功response/eventを描画する。

### Whitespace棋譜との互換性を持たせない

元実装のWhitespace変換APIとAWS依存の保存形式は移植しない。後続Issueでは「実行可能ななでしこコードそのものを棋譜にする」方式を採用する。
